# Feature - bilingual interface (ru/en)

## Status

The client did not have an intentional language boundary: most of it was English,
while mapper strings added during early development were Russian. For `v0.2.0` the
authored mapper UI and its API messages are standardized on English. MUD output,
room and zone names, movement vocabulary, aliases, commands, and parser fixtures
remain in their source language because they are game data, not interface copy.

The Russian mapper wording was not discarded. It is recorded below as the source
for the `ru` catalog extraction.

The catalog foundation is now implemented: `app_settings.language` persists the
instance-wide `en`/`ru` choice with English as the explicit default, both HTML
entry points receive the normalized locale at boot, and Settings exposes the
choice. Applying a language reloads Settings and broadcasts the committed locale
to already-open game tabs, which update active and future mapper panes without a
game reconnect. The boot injection keeps locale reads out of the game loop.
Typed, dependency-free TypeScript and Go catalogs provide completeness,
extraction, fallback, and compact-layout tests.

Server-side mapper soft failures now retain their historical English `reason`
while also returning a stable code and typed arguments. The same arguments
reconstruct the exact text after a JSON round trip, including Russian plurals
and optional route-summary clauses. Recording guards and controls, route and
walk results, cell/edge/portal writes, undo, archive import, and room-format
profile validation/CRUD/replay use the cached instance locale at their HTTP or
WebSocket serialization boundary. Opaque archive/parser/storage diagnostics are
kept in separate `*_detail` fields; commands, map content, direction vocabulary,
and game output are never translated.

The remaining mapper server boundary is now covered as well: zone move/rename,
reconciliation, map-set/session mapper administration, tracker
`position_reason`, and mapper-profile fallback warnings carry stable codes and
opaque details. A committed instance-language change broadcasts one lightweight
`app_language_changed` message per active session without reloading the VM,
parser, tracker, or transport; concurrent updates serialize DB commit, locale
cache, and the final event in that order. Recording lifecycle and conflict
reasons use the same REST/WebSocket code-first boundary, and profile replay
returns parser/compiler diagnostics in the validation JSON envelope. The client
mapper boundary is complete: canvas controls, room Knowledge and its inhabitant
catalogue/forms, mapper-profile and map-set administration, and the session
selectors use explicit typed en/ru catalogs. Extraction audits allow only
documented parser vocabulary, wire enums, regexes, commands, and opaque game data.

## Decision

- Support `ru` and `en` catalogs rather than maintaining separate translated views.
- Store one instance-wide language in `app_settings`. RubyMUD is local-first and
  single-user; per-session overrides would make shared Settings language ambiguous
  without serving a current use case.
- Translate strings authored by RubyMUD. Never translate server output, map content,
  commands, aliases, room-format patterns, or direction words consumed by parsers.
- Keep mapper API reasons in the same catalog as the browser copy because the pane
  renders those reasons verbatim.
