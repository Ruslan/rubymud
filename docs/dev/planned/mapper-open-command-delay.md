# Mapper: задержка между открытием прохода и движением

## Статус

Feature request подготовлен 2026-08-22. Реализации пока нет.

До реализации проходы, которым требуется время после команды открытия, следует
помечать `no_route=true`: они остаются видимыми и пригодными для ручного движения,
но автоматическая ходилка не выбирает их.

## Наблюдаемый сценарий

В Хилло комнаты `Беседка` и `Тупик` находятся на одной клетке разных этажей:

```text
Беседка  {x=4,y=-18,l=0}
   D
   |
   U
Тупик    {x=4,y=-18,l=-1}
```

Проход активируется отдельно с каждой стороны:

- `Беседка -> D`: `повернуть рычаг`, затем `вниз`;
- `Тупик -> U`: `нажать кнопку`, затем `вверх`.

Runtime-лог 2026-08-22 показывает существенную задержку. После нажатия кнопки
сервер немедленно вернул prompt без `U`; две ранние попытки движения получили
`Увы, Вы не можете идти в этом направлении.`. Примерно через две секунды сервер
сообщил, что в потолке появилось отверстие, и только тогда `U` стал доступен.

У комнаты уже корректно хранится `mutable_exits`: появление и исчезновение люка
не означает смену комнаты. Сам активируемый проход должен жить в ручном слое
топологии (`mud_room_mark_edge`), чтобы перезапись room block его не стирала.

## Проблема текущей ходилки

У directed edge уже есть два разных атрибута:

- `phrase` — команда, которая **заменяет** направление и сама переносит игрока;
- `open_cmd` — действие перед обычным направлением.

`phrase="повернуть рычаг"` здесь неверна: ходилка сочтёт действие завершённым
переходом. `open_cmd` выражает смысл правильно, но сейчас map-walk отправляет
результаты `open_cmd` и направление подряд, без ожидания.

В VM существует асинхронный `#delay`, однако route scripts намеренно запрещают
timer/delay effects. Они выполнялись бы вне lifecycle конкретного map-walk job,
а отложенное направление выглядело бы трекеру как постороннее ручное движение.
Блокирующий `#sleep` отсутствует и добавлять его в игровой цикл нельзя.

## Предлагаемый контракт

Добавить направленный атрибут ребра `open_delay_ms`:

```json
{
  "door": true,
  "open_cmd": "нажать кнопку",
  "open_delay_ms": 3000
}
```

Семантика:

1. Значение `0` сохраняет текущее поведение без задержки.
2. Положительное значение означает неблокирующую паузу после успешной отправки
   всех MUD-команд из `open_cmd`, но до отправки команды перехода.
3. Атрибут принадлежит одной направленной грани. Обратная сторона может иметь
   другую команду и другую задержку.
4. Задержка имеет смысл только вместе с `door=true` и непустым эффективным
   opening action. Неконсистентная запись должна отклоняться, а не молча
   становиться неактивной.
5. Значение должно быть целым, конечным и ограниченным. Предлагаемый диапазон:
   `0..30000` мс.
6. `phrase`, `open_cmd` и `open_delay_ms` остаются разными понятиями. Поддержка
   `#sleep` или scheduler-команд внутри route scripts в эту задачу не входит.

Название поля намеренно описывает задержку после opening action, а не общий
sleep шага. Это не даёт превратить маршруты в произвольные медленные скрипты.

## Runtime state machine

После отправки opening action map-walk должен перейти в явную фазу ожидания:

```text
dispatch opener -> waiting_open -> dispatch movement -> awaiting room -> next hop
```

Требования:

- использовать timer, не `time.Sleep`;
- не держать `mapWalkMu`, `mapMu`, I/O gate или storage operation во время паузы;
- привязать callback к `job id` и поколению/hop, чтобы старый timer не мог
  продолжить новый маршрут;
- Stop, replacement route, disconnect, manual movement и invalidation обязаны
  отменять ожидание и гарантировать отсутствие позднего movement tail;
- opener не должен отправляться повторно после завершения таймера;
- pending move и expected landing регистрируются непосредственно перед отправкой
  направления, а не на время ожидания;
- browser state должен отличать ожидание механизма от ожидания новой комнаты.

Автоматическое распознавание факта открытия по prompt, scan или произвольной
фразе MUD в этот feature request не входит. Фиксированная bounded-задержка —
намеренно простой и серверно-настраиваемый контракт.

## Storage, API и UI

Изменение проходит через все штатные слои:

- SQLite migration добавляет directed edge attribute с default `0`;
- storage read/write, undo и fork сохраняют его вместе с остальными атрибутами;
- REST edge editor и `mud_room_mark_edge` принимают, валидируют и возвращают
  `open_delay_ms`;
- compact MCP topology output показывает только ненулевое значение;
- mapper UI редактирует задержку рядом с `open_cmd`, с единицами измерения и
  понятной ошибкой диапазона;
- topology invalidation обновляет активную игровую вкладку без restart;
- path result сообщает задержку для диагностики маршрута.

Существующие map sets и ребра сохраняют точное прежнее поведение.

## Repro-first тесты

### Go unit/integration

1. Сначала воспроизвести текущий дефект: opener и direction появляются на wire
   подряд, хотя edge требует задержку.
2. С управляемым clock/timer доказать, что direction отсутствует до deadline и
   отправляется ровно один раз после него.
3. Проверить отдельные задержки прямой и обратной directed face.
4. Stop, route replacement, disconnect и manual movement во время ожидания не
   оставляют позднего направления.
5. Timer старого job/hop не продолжает новый job и не повторяет opener.
6. Ошибка/short write opener не запускает timer и direction.
7. Несколько команд opening script полностью отправляются до начала ожидания;
   запрещённые async VM effects по-прежнему отказывают до первого write.
8. Storage round-trip, undo/fork, REST и MCP проверяют `0`, `3000`, границы и
   невалидные значения.
9. `go test -race` покрывает cancel/expiry/replacement interleavings.

Тесты state machine не должны ждать реальные три секунды.

### Live E2E

Расширить loopback MUD emulator активируемым вертикальным проходом:

1. Изначально `D/U` отсутствуют.
2. Opener немедленно возвращает prompt, но открывает проход только после
   контролируемой задержки.
3. Раннее направление получает штатный refusal.
4. Map-walk с `open_delay_ms` отправляет opener, не отправляет ранний direction,
   затем попадает в целевую комнату и сохраняет зелёную позицию.
5. Обратный путь использует другую opening command.
6. Отмена во время ожидания оставляет персонажа в исходной комнате.

E2E ожидает события/trace с deadline, а не использует фиксированные sleeps в
Playwright orchestration.

## Acceptance criteria

- `Беседка -> Тупик` и `Тупик -> Беседка` безопасно проходятся автоматическим
  маршрутом с разными opening commands и задержками.
- Ни один timer после отмены или замены маршрута не отправляет команду в MUD.
- Main game loop и WebSocket/UI updates не блокируются во время ожидания.
- Обычные двери с `open_delay_ms=0` работают без изменения поведения.
- Ручной topology mark и атрибуты переживают повторную запись room block.
- После подтверждённого E2E для люка можно снять временный `no_route=true` с
  обеих directed faces.
